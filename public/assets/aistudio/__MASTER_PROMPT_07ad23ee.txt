# 2. IDENTITAS DAN KONTEKS PROYEK

Nama aplikasi: **PUSAT GAMES BUDDHIS**

Jenis aplikasi: Platform permainan edukasi Buddhis berbasis web.

Teknologi frontend yang sudah digunakan:

- HTML5.
- Tailwind CSS.
- JavaScript murni (Vanilla JavaScript).
- HTML5 Game.
- iframe dengan srcdoc.
- localStorage sebagai penyimpanan data versi lama.

Kondisi aplikasi saat ini:

Aplikasi masih menggunakan penyimpanan lokal browser. Akibatnya, perubahan data yang dilakukan oleh administrator pada Komputer A tidak otomatis tersedia pada Komputer B.

Target pengembangan:

Mengubah aplikasi menjadi sistem Full-Stack dengan database SQL pusat sehingga seluruh data utama tersimpan secara terpusat dan dapat diakses oleh administrator maupun pengguna dari perangkat berbeda.

Contoh alamat produksi:

- Aplikasi: `https://games.namasekolah.com`
- API: `https://games.namasekolah.com/api/v1`
- Area permainan atau konten game: dapat menggunakan subdomain terisolasi apabila diperlukan.
- Database: PostgreSQL pada server pusat.

**Prinsip utama:**

Database SQL merupakan satu-satunya sumber data utama (Single Source of Truth). Browser tidak boleh lagi menjadi tempat penyimpanan permanen untuk data inti aplikasi.

# 4. ARSITEKTUR TEKNOLOGI

Gunakan arsitektur berikut sebagai standar implementasi.

## 4.1. Frontend

- HTML5.
- Tailwind CSS.
- Vanilla JavaScript ES6+.
- Fetch API sebagai komunikasi utama dengan backend.
- Socket.IO Client untuk notifikasi sinkronisasi data.
- iframe srcdoc untuk permainan HTML5 portable.
- Font Awesome untuk ikon yang sudah digunakan.
- Chart.js atau library sejenis jika aplikasi membutuhkan grafik statistik.

Jangan memperkenalkan React, Vue, Angular, atau framework SPA lainnya kecuali benar-benar diperlukan dan mendapat persetujuan.

## 4.2. Backend

Gunakan:

- Node.js LTS yang didukung pada saat implementasi.
- Express.js.
- REST API.
- Socket.IO.
- Prisma ORM.
- Zod untuk validasi data.
- Multer untuk upload file.
- Argon2id atau bcrypt untuk hashing password.
- Helmet untuk security headers.
- Express Rate Limit untuk pembatasan request.
- Logging terstruktur.
- PostgreSQL sebagai database utama.

Jika lingkungan hosting hanya mendukung MySQL, sediakan alternatif skema dan konfigurasi MySQL tanpa mengubah kontrak API frontend.

## 4.3. Database

Gunakan PostgreSQL dengan struktur relasional.

Pastikan terdapat:

- Primary key.
- Foreign key.
- Unique constraint.
- Index.
- Relasi antarentitas.
- Timestamp `created_at` dan `updated_at`.
- Validasi data.
- Transaksi database.
- Kebijakan penghapusan data.
- Mekanisme migrasi database.

## 4.4. Arsitektur Komunikasi

Gunakan pola:

`Frontend → REST API → Backend Service → Prisma ORM → SQL Database`

Untuk sinkronisasi:

`Admin A → API → Database → Socket.IO → Admin B`

`Admin B → API → Database → Admin A`

Socket.IO digunakan untuk memberi tahu klien bahwa suatu data berubah. Data yang sebenarnya tetap diambil dari API dan database, bukan hanya dikirim melalui event socket.

Pastikan event sinkronisasi hanya dikirim setelah transaksi database berhasil diselesaikan.

Sediakan mekanisme fallback berupa polling berkala jika koneksi WebSocket terputus.

# 7. SISTEM UPLOAD DAN GAME PORTABLE

Fitur ini merupakan bagian penting dari aplikasi dan tidak boleh dihilangkan.

Admin harus dapat menambahkan game baru melalui Admin Hub Studio.

Dukung format berikut:

- `.html`
- `.json`
- `.js`
- `.css`
- `.zip` untuk paket permainan beserta aset pendukung, apabila diperlukan.

Terapkan aturan format:

1. File HTML tunggal dapat disimpan sebagai `html5_code` apabila ukuran masih berada dalam batas yang ditetapkan.
2. File JSON harus divalidasi dan memiliki struktur manifest yang jelas.
3. File JavaScript tidak boleh langsung dianggap sebagai game lengkap tanpa loader atau manifest yang valid.
4. Game dengan banyak aset sebaiknya disimpan sebagai paket di storage server, sedangkan database menyimpan metadata dan lokasi filenya.
5. File ZIP harus diperiksa dari path traversal, file berbahaya, dan ukuran hasil ekstraksi.
6. Backend tidak boleh mengeksekusi file permainan yang diunggah.
7. File game harus disajikan melalui mekanisme yang aman dan terpisah dari proses backend.

Buat standar `manifest.json` untuk permainan portable yang membutuhkan banyak aset.

Contoh:

```json
{
  "title": "Nama Game",
  "version": "1.0.0",
  "entry": "index.html",
  "assets": [
    "index.html",
    "style.css",
    "game.js"
  ]
}
```

## 7.1. Sistem iframe srcdoc

Pertahankan cara menjalankan game melalui:

```javascript
iframe.srcdoc = gameHtml;
```

Namun, jangan hanya berfokus pada keberhasilan menampilkan permainan. Terapkan isolasi dan keamanan konten.

Ketentuan:

- Game tetap dapat menjalankan JavaScript yang memang dibutuhkan.
- Game responsif di berbagai ukuran layar.
- Area game tidak boleh merusak navigasi halaman utama.
- Gunakan atribut sandbox dengan izin minimum yang diperlukan.
- Jangan memberikan izin akses yang tidak dibutuhkan.
- Batasi akses top navigation, pop-up, dan navigasi keluar.
- Gunakan Content Security Policy yang sesuai.
- Jangan memberikan akses DOM halaman induk kepada game.
- Hindari kombinasi izin iframe yang memungkinkan game mengambil alih halaman utama.
- Pertimbangkan origin/subdomain khusus untuk konten game yang tidak dipercaya.

Jika game membutuhkan aset eksternal, buat sistem resolusi URL aset yang konsisten dan aman.

Jangan mengubah source code game sedemikian rupa sehingga permainan lama tidak lagi berfungsi.

# 8. AUTENTIKASI DAN KEAMANAN ADMIN HUB STUDIO

Pertahankan Admin Hub Studio sebagai pusat pengelolaan aplikasi.

Namun, ubah proteksi password yang hanya berada di JavaScript menjadi autentikasi server-side.

Persyaratan:

1. Password tidak boleh disimpan dalam bentuk teks biasa.
2. Gunakan Argon2id atau bcrypt untuk hashing password.
3. Password administrator tidak boleh ditanam di HTML atau JavaScript.
4. Hak akses harus diperiksa di backend.
5. Implementasikan role-based access control (RBAC).
6. Terapkan pembatasan percobaan login.
7. Terapkan rate limiting.
8. Sediakan mekanisme logout.
9. Sediakan manajemen sesi.
10. Catat aktivitas administrator melalui audit log.

Utamakan session authentication menggunakan cookie:

- HttpOnly.
- Secure pada HTTPS.
- SameSite sesuai kebutuhan.
- Perlindungan CSRF.
- Masa berlaku sesi yang jelas.

Jangan menyimpan token autentikasi permanen di localStorage.

Jika menggunakan JWT, jelaskan dan implementasikan dengan benar mekanisme refresh token, rotasi token, dan pencabutan sesi.

Buat matriks izin setiap role untuk seluruh tab Admin Hub Studio.

# 9. FRONTEND INTEGRATION

Perbarui seluruh fungsi JavaScript supaya mengambil dan menyimpan data melalui backend API.

Gunakan `fetch()` sebagai standar komunikasi.

Buat satu modul terpusat, misalnya:

`/assets/js/api.js`

Modul ini harus menangani:

- Base URL API.
- Authorization/session handling.
- Pengiriman JSON.
- Upload multipart/form-data.
- Penanganan HTTP error.
- Parsing response.
- Timeout.
- Penanganan jaringan terputus.
- Pesan notifikasi kepada pengguna.

Contoh dasar:

```javascript
const API_BASE = "/api/v1";

async function apiRequest(endpoint, options = {}) {
  const response = await fetch(`${API_BASE}${endpoint}`, {
    credentials: "same-origin",
    ...options
  });

  const result = await response.json().catch(() => null);

  if (!response.ok) {
    throw new Error(
      result?.message || "Terjadi kesalahan pada server"
    );
  }

  return result;
}
```

Sesuaikan implementasi akhir dengan kebutuhan Content-Type, FormData, CSRF, dan sesi autentikasi.

# 10. SINKRONISASI REAL-TIME ANTARADMIN

Buat sistem sinkronisasi antarperangkat menggunakan Socket.IO.

Contoh penggunaan:

Admin A pada Komputer A menambahkan game baru.

Alur yang wajib terjadi:

1. Admin A mengirimkan data melalui API.
2. Backend memvalidasi input dan file.
3. Backend menyimpan data melalui transaksi database.
4. Setelah transaksi berhasil, backend mengirimkan event Socket.IO.
5. Semua klien admin yang memiliki izin menerima notifikasi perubahan.
6. Klien melakukan refresh data dari API.
7. Game baru langsung muncul pada Komputer B tanpa harus mengisi ulang data secara manual.

Terapkan konsep yang sama untuk:

- Penambahan game.
- Pengubahan game.
- Penghapusan atau pengarsipan game.
- Penambahan kategori.
- Perubahan nama kategori.
- Perubahan ikon kategori.
- Perubahan testimonial.
- Perubahan Hero.
- Perubahan Stupa dan Candi.
- Perubahan konfigurasi beranda.
- Perubahan data administrasi lainnya.

Buat event yang konsisten, misalnya:

```text
game:created
game:updated
game:deleted
category:created
category:updated
category:deleted
testimonial:updated
homepage:updated
stats:updated
```

Ketentuan:

- Verifikasi autentikasi koneksi socket.
- Batasi event berdasarkan role.
- Jangan mengirim data rahasia melalui event publik.
- Gunakan room berdasarkan kebutuhan akses.
- Hindari duplikasi event.
- Tangani reconnect.
- Sediakan fallback polling.
- Pastikan perubahan dari database tetap tersedia meskipun socket terputus.
- Jika beberapa administrator mengedit data yang sama, gunakan mekanisme optimistic concurrency/versioning atau `updated_at` untuk mendeteksi konflik.

**Jangan mengasumsikan hosting mendukung Node.js.**
